## New defects introduced by the fixes

**N1. The prereg does not state the process rule the driver enforces (text-only; fix before the freeze).**
- Prereg §3 (`docs/C10R_EXP2_LOCATIONCTL_PREREG.md:28`) says an exclusive-GPU window is "enforced by a full process check before, after preflight and during the run" and that any failure is INVALID. The driver instead (a) defines contenders as descendants of the roots listed in `read_replay.py:297-322`, (b) tolerates up to two consecutive contender observations or probe failures during the run, and (c) lets the editor finish after INVALID is latched (`run_replay.sh:71-72`). Pre-dispatch checks are strict (`:65-66`).
- Why it matters: the registered rule and the executed rule should be the same text, or a reader of the frozen prereg will believe contention for one or two seconds is INVALID when it is not. A foreign GPU job that starts and stops inside about three seconds passes.
- Fix: add one sentence to §3, for example "Contenders are descendants of the model roots named in `read_replay.py` (edit/prepare/check_equivalence scripts, c10 drivers, notebook kernels, Ollama, llama.cpp, LM Studio, `claude --safe-mode`); a window is INVALID after three consecutive polls of the same contender or three consecutive failed probes; earlier polls are tolerated and logged." Prereg text only; no code or hash change.

**Residual risks (not blockers; all in code that cannot be exercised without the GPU run):**
- R1. The contender rule has no catch-all for an unnamed Python/torch job (`read_replay.py:297-322`). The v2 review's suggestion to match interpreters under the venvs was deliberately not adopted (impl report, issue 2). The operator's closeout list covers the loop and model servers only. Practical exposure: any other `torch` script the operator starts during the window.
- R2. The dispatch, Popen, three-poll loop, signal teardown and post-run receipt code (`run_replay.sh:151-230`) have never been executed end to end; the tests exercise the extracted `exclude` function and the closeout block (`test_replay.py:207-245`). I walked the success path and found no defect (imports resolve; `launch` JSON round-trips equal; `edit.py` reads `REPLAY_LAUNCH_PATH` and the caller's `arm` and `run_dir` locals, and `prepare.py:201-209` supplies both in `evaluate`). The first live run is still the first test of this block.
- R3. `stop_owned` raises `ValueError` if any retained owned PID sits in a process group other than the editor's (`run_replay.sh:87`). That is on the failure-teardown path only; on a failure the editor group would then not be signalled by this call. Not the monitor, not triggered in normal operation.
- R4. `own` and `groups` exempt the runner's ancestors and its whole process group (`read_replay.py:350-352, :364-365`). If the runner is launched without job control (shared process group with a loop started from the same shell), that loop would be exempt. Launch from an interactive tmux pane gives the runner its own group.
- R5. Contention under about three seconds is not caught, and an INVALID latched mid-run does not stop the editor (up to about 50 minutes of wasted GPU time). Both follow the stated policy; they are cost, not correctness.
- R6. The reader re-validates the precheck record with `precheck_runtime()` (`read_replay.py:601-607`, `tokenizer_precheck.py:19-24`). Re-running the reader later by hand with a different interpreter, or with `PYTHONPATH` set, fails `tokenizer_equality_before_dispatch`. Use the pinned `.venv/bin/python`, as the runner does (`run_replay.sh:222`).
