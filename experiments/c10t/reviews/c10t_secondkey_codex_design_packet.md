Run this review and answer concisely and specifically:

## 0. Where this sits, and what it is

The **§C write path** read against the **§8.9 bar** (held-out paraphrase, full-sequence, top-1). Every arm so far has keyed each fact once, at the subject's last token, and asked one target `z` to carry the whole 4–6-token value from that one position. This arm keeps that request unchanged and adds, per fact, **one more request keyed at a token inside the value**, whose target is the remainder of the value: 48 requests, 48 keys, two `z` per fact, targets as the engine computes them per key (no `Z_OVERRIDE`). The position is not chosen by hand: it is the token before the maximum-surprisal boundary of the value under the base model (H-10) or the maximum covariance-leverage position kᵀΣ⁻¹k under the band covariance (H-5), computed in step 0 and published before the run.

**The e2e map:** write layer, compile step (§8.1 D20 solve), the **key (address) definition** — the first arm of the program to change the address side for a coined value rather than the target or the solve geometry. The sequence's criterion 3 ranks realisation arms above address arms; this one is here because the later value tokens currently have no objective at any key position but the subject's, and a second key is the cheapest closed-form way to give them one (step 2 row, `recommended_sequence.md:21`). Nothing in the read, governance or deployment layers is touched. **What it displaces in §0.3:** per the sequence it runs after step 1 and before the engine-path arms I-1 / I-2 (step 6); it is a live H-10/H-5 lead, not a §0.3 falsifier of its own.

**What this experiment can and cannot conclude.** A pass advances a candidate. A miss, at any stage, means *this candidate configuration was not advanced* — one position rule per fact, one extra key, engine targets, this solve budget — and nothing more: a NULL does not say a value-internal key cannot carry the continuation, and the stub's "a second closed-form key alone cannot carry the continuation" is **not** adopted as a NULL reading (departure from the stub, `prereg_stubs.md:34`). A LEAD is a write-path mechanism lead under one relation label, not §8.9 contract closure. The second key is a frame-plus-value-prefix key, so the arm also measures something CORPUS/43 did not: whether a key taken *inside the value* is stable across phrasings of the same fact (§3, diagnostic e).

## 1. Question and hypotheses

- **H-T1 (direct address):** a second key at the chosen value-internal position, with its own target fit to the remaining value tokens, raises A7 `para_full` over the same-run single-key arm with locality held, because the continuation tokens receive a direct write instead of depending on one residual at the subject position.
- **H-T0 (null — the prior):** it does not, in this configuration. CORPUS/44 says ≈ 3 % of the target is realised at the keyed position; a second keyed position with its own ≈ 3 % does not change the held-out count, and the held-out prompts never contain the frame the second key was taken in.
- **H-T2 (trade-off / bleed):** it raises the count but the 24 second keys are near-collinear across facts (the CORPUS/43 geometry, now at a value-internal token) and the continuation fires on same-frame prompts with other subjects, or the write grows.
- **H-T3 (key side):** the second key does not transfer across phrasings — its cosine to itself under the held-out templates is low — so the continuation is written at an address the held-out prompts never reach. This reading is only available because diagnostic e (§3) is recorded.

## 2. Design (engine unmodified; the second request enters through the harness request builder, the seam CORPUS/43 used; step 0 offline; one harness pass; a second process when the label needs it)

**How a key inside the value is addressed (LAW#4 — authored from the sources read 2026-10-06).**
- The engine keys every request at the last token of `request["subject"]` inside `request["prompt"]`: `compute_ks` builds `context.format(request["prompt"])` with `words=request["subject"]` per request and context template (`memit_dry_run/memit/memit/compute_ks.py:19–37`), takes the input side of `rewrite_module_tmp` (`:35`, the `[0]` at `:37`), and averages over the templates per request (`:44–49`).
- The hparams fix `fact_token: "subject_last"` (`configs/hparams/qwen25_3b_memit_hparams.json:5`), which `get_module_input_output_at_words` turns into `subtoken="last"` (`compute_z.py:208–216`).
- The index comes from `get_words_idxs_in_templates` (`memit_dry_run/memit/rome/repr_tools.py:43–99`): the template must contain exactly one `{}` (`:52–54`); the prefix before it must end in a space, which is stripped (`:66–67`) while the word becomes `" " + word.strip()` (`:70`); prefix, word and suffix are tokenised **separately** (`:75`) and the keyed index is `prefixes_len + words_len − 1` (`:85–90`). Nothing in that path looks at the word's content: the keyed token is whatever token ends the `subject` string.
- The harness already exploits this: the CORPUS/43 last-token cells pass `prompt="The capital of {}"`, `subject=f"{c} is the city of"` so that `subject_last` keys the final `" of"` (`experiments/track_c/c10e_bandknob.py:477–478`), with a validity print that decodes the keyed token from the whole-string tokenisation (`:481–485`).

**The second request, therefore:** `prompt = "The capital of {}"`, `subject = f"{c} is the city of" + tok.decode(V_ids[:j])`, `target_new.str = tok.decode(V_ids[j:])`, where `V_ids = tok(" " + V)["input_ids"]` is the A7 value's tokenisation exactly as the canonical request's target (`c10e_bandknob.py:96–97` prepends the space; `compute_z.py:41–43` tokenises `target_new.str` standalone) and `j ∈ {1, …, n−1}` is the published key position (value token `j`, 1-based; token `n` is excluded because its remainder is empty). The second request is built by hand, not through `req()`, which would prepend a second space (`:97`). What the engine then does with it:
- rewriting prompts are `context.format(prompt) + tok.decode(target_ids[:-1])` (`compute_z.py:46–50`) formatted with the extended subject (`:53–57`); the targets are the remainder's ids sliced off the end of each tokenised prompt (`:60–65`);
- the lookup index is the extended subject's last token (`:67–73` → `find_fact_lookup_idx`, `:234–256`); `delta` is added there (`:98–99`) and `target_init` is that position's base activation (`:95`);
- the loss is the mean NLL over the remainder tokens (`:149–150`) plus the KL term on `"{} is a"` formatted with the extended subject (`:50`, `:54`, `:127–128`) plus weight decay (`:154–156`); it stops at total loss < 0.05 (`:164`) or 25 steps (`v_num_grad_steps`, hparams `:6`); delta is clamped to `0.75 × ‖target_init‖` (`:175–178`, hparams `:3`);
- in `my_edit` the two requests of a fact are two columns of `K` (`c10e_bandknob.py:196`) and two columns of `zs − cur` (`:191`, `:197–202`), solved jointly at each band layer (`:209–211`) and added to the key cache (`:218–220`); the canonical request is unchanged (`req(CANON, c, V)`, `:480`); `Z_OVERRIDE` stays `None` (`:407`) and `Z_OVERRIDE_HITS` must read 0.
- Request order is pinned blocked: the 24 canonical requests first, in `FICTION` order, then the 24 second requests, so indices 0–23 equal the single-key arm's list; the closed form is order-invariant (`:209–211`, `:220`).

**Request admission (step 0, mechanical; a fact whose chosen `j` fails is INADMISSIBLE at that `j` and the rule's argmax is re-taken over admissible positions only):**
