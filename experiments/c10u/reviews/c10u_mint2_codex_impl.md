## Implementation decisions and prereg issues retained

1. **Context generation versus first-run order.** §2 says the A7-multi process generates contexts before minting, yet §7 requires all three F mint1 behaviors first. A dedicated no-edit/no-behavior A7-multi precursor freezes the same engine-generated cache; the counted fourteen-run order is unchanged. Context generation itself is verified to leave the vocabulary and all271 spare rows unchanged. This is an explicit scheduling resolution, not an early multi behavioral comparator.
2. **Where to solve/capture targets.** Each (block,kind,seed) admission calls the unmodified engine once for each of24 targets, stores the exact returned z and hashes the tensor; every behavior/replica reconstructs the same registered rows, checks whole pre-recall and replays that frozen target through `Z_OVERRIDE`. This avoids a second independent z solve masquerading as the captured target. The native/override/cache proof and existing LAW#5 run before any scientific behavior is accepted. Multi likewise captures its own targets for geometry and an audited one-A7 override.
3. **No-write step0 versus per-process LAW#5 wording.** Admission/context processes do no FFN edit, so their P3 solves and tokenizer probes are provisional preparation protected by fingerprint/reference checks. Every process that applies a behavioral or artifact-save edit performs the new-wrapper proof and standard LAW#5 before trusting behavior. A stage's admission is not a scientific conclusion. Running a transient FFN LAW#5 inside an explicitly no-write admission would conflict with the stated step0 boundary.
4. **Numeric inertness tolerance.** The frozen document requires proof but supplies no number for the two new wrappers. The pure reader uses ≤1e-5 for relative whole-weight difference, copied-cache difference and maximum next-token probability difference, with exact expected override counters. The existing reviewed LAW#5 tolerances (<0.05 expression and <3 locality) are preserved and rechecked. Final/loss-layer fit differences are reported without a new threshold.
5. **FP32 draw versus actual FP16 rows.** Reviewed N produces CPU FP32 rows and the tied model stores FP16 rows. Hashes of the raw deterministic draw/prefixes prove cross-count pairing; a separate hash of the applied FP16 rows proves the write left the embedding untouched.
