## R1. Git records, Drive bulk, no Intel route to memit

The selected direction is GitHub Git for research records, Google Drive for bulk, and M3-only memit (`B/r2_redesign_operator_ruling.md:7`). Recorded artifact policy puts JSON, manifests, hashes, summaries, CORPUS, ledgers and code in Git; irreplaceable bulk goes to Drive (`EXPERIMENT_RUNBOOK.md:272–275`).

PROPOSED data path: M3 publication → approved GitHub origin → Intel pinned checkout → rebuildable research views; M3 completed bulk → verified Drive generation → Intel-local retrieval. Intel never opens memit directly or through a proxy, even when M3 is idle. Research views retain source commit/path/hash and coverage; they cannot manufacture missing evidence. Preserve the separate publication and MathLab authority requirements (`B/integration_plan.md:28`).
PROPOSED Git acquisition: fetch only the reviewed GitHub origin, select an explicitly published commit, verify required manifests and hashes, and keep writable builder copies separate from protected records. A missing/unpublished record is labelled unavailable at that revision; no fallback to an M3 checkout or memit. Pin each query/publication to its actual source commit; update derived views as a paired generation. Intel remains prohibited from local inference, editing, training and embeddings (`B/decisions_log.md:109–111`).
PROPOSED bulk acquisition: request a manifest identity from Git, fetch only its exact verified Drive object/version into budgeted Intel-local storage, compare size and SHA-256, and publish locally only on full match. A partial download stays incomplete. Absence, auth failure or capacity refusal leaves the research request waiting; Intel's own queries/builds continue on labelled available records.

PROPOSED enforcement: physically retain memit on M3; withdraw every memit export, file-service endpoint, disk-access SSH/SFTP/SCP account/key, forwarding route and old R2 ingress capability available to Intel. Disable automatic mounts/reconnects and never pass memit descriptors or source streams to Intel. Intel has Git/Drive access, not an M3 general shell. Disable any legacy M3→Intel checkpoint sender. Both old and newly configured routes must satisfy this boundary.
PROPOSED dashboard exception is telemetry only: M3 independently publishes bounded status on internal control storage; an Intel-facing forced status endpoint can read only that publication and cannot accept paths, execute arbitrary commands or access memit. No source files, bulk or disk handles pass through it. Local M3 collection is distinct from Intel disk access; reconcile the advisory-only dashboard interface (`B/dashboard_host_status_record_v3.md:93,261–265`).
**Test:** commission with an Intel-owned credential/account: Git fetch and a known Drive-object fetch must succeed; all attempted memit mount/share/SSH/SFTP/SCP/proxy/symlink routes and retained old R2 capabilities must fail before source bytes or handles are returned. Inspect actual exports, mounts, service/account permissions and autostarts on both hosts; repeat after restart and configuration change. A successful disk route or uninspectable configuration is FAIL; text searches alone are insufficient.

## R2. M3-local science/backup exclusion without a descendant list

Recorded admission refuses other non-exempt Python executables and local model runtimes; exemptions are exact command forms (`tools/c10w_p2_gate.py:19–54`). Failed/empty process observation refuses, and tmux errors except the exact no-server case refuse (`tools/c10w_p2_gate.py:73–84`). Fingerprint, GPU and dispatch checks all contribute to admission (`tools/c10w_p2_gate.py:151–158`). Its executable classifier does not match rclone (`tools/c10w_p2_gate.py:22,51–53`).
Today's backup has its own lock directory and retained-lock interruption behavior, then starts and waits for a background rclone sync (`tools/backup_gdrive.sh:15,49–80,121–142`). This is backup serialization, not a common science/backup gate. Status health checks owner/child PIDs for incomplete runs; they are not whole-run descendant closure (`tools/backup_gdrive_status.py:571–586`).

PROPOSED primary mechanism: **separate dedicated macOS activity accounts**, for example `llmdb-science` and `llmdb-backup`, with distinct pinned numeric UIDs. All science and anything it starts run under the science UID; all backup/Drive maintenance and its helpers run under the backup UID. The operator/team account remains separate, with its tmux sessions and remote access untouched by routine switches. Account names are PROPOSED examples, not provisioned identities.

- One protected M3-local controller, common lock and durable mode record live on internal control storage, outside either activity account's writable files. Record host/boot/controller epoch, pinned UIDs, mode, run identity, reservations and unresolved outcomes. A trusted controller outside the activity UIDs owns serialization and holds the activity lock throughout each run, including backup enumeration, hashing, verification and receipt completion. Either account's root process exiting or a kernel lock becoming free never clears the durable mode by itself.
- Before BACKUP starts, obtain a successful **full host process-table snapshot** and require **no process whose real or effective UID is the science UID**; before SCIENCE starts, require no process whose real or effective UID is the backup UID. Filter numeric credentials, not names, argv, ancestry, Python matches or P8. Any process for the opposing account counts, including shells, orphans, detached helpers and launchd/agent jobs; there are no service/idle exemptions. This defines a complete activity population by account rather than by a descendant list, conditional on the privilege and launch restrictions below. **UID-quiescence acceptance:** the selected observation primitive must have an evidenced successful-empty-set guarantee that cannot miss a surviving activity lineage under fork/exit churn, disappearing PIDs, PID reuse or incomplete credential reads. A disappeared or unreadable PID cannot simply be discarded as harmless; ambiguity refuses switching. Freeze and justify that guarantee before activation; repeated scans or an independent implementation alone are not proof. No macOS observation API is selected by this requirement.
- Under that same lock, fence opposing-account future starts, validate current durable mode/account bindings and complete process observation, commit the selected mode/reservation, then release only the selected fixed-UID payload to execute. Keep the fence through the run. After it ends, disable/revoke its pending launch capabilities and repeat the full UID check before committing quiescence or switching mode. A check followed by an independently racing launcher is not admissible. Revalidate after controller loss; absence alone cannot override an unresolved durable lifecycle.
- The science/backup accounts are non-admin, non-interactive workers without operator/root passwords, inherited administrator credentials, cached sudo authorization, sudoers/NOPASSWD grants or reusable authorization rights. PROPOSED deny privilege-changing use of `/usr/bin/sudo`, `/usr/bin/su`, `/usr/bin/login`, `/usr/libexec/authopen`, `/usr/libexec/security_authtrampoline`, their installed variants, and any other installed setuid/setgid executable or privileged helper to change UID or submit arbitrary work under another UID. Commission actual paths/permissions and service authorization; a password prompt alone is not protection against cached or delegated rights. No activity may edit the controller, account bindings, launch policy or credentials. Confinement commissioning must also exclude worker writes through groups/ACLs to trusted scripts, executables, imported modules, hooks and configuration used by operator/controller/daemon processes, including replacement through writable parent directories; a read-only file is insufficient if its directory permits substitution.
- The trusted launcher accepts only reviewed fixed activity/UID and source bindings, never arbitrary privileged commands, and drops real/effective/saved UIDs, GIDs and supplementary privileges before payload execution. With privilege-changing/delegation routes unavailable, fork/exec/reparenting/daemonization retain the activity UID, so a surviving process cannot escape the account check. Account renumbering, alias UIDs, credential uncertainty or unreviewed setuid/helper changes invalidate commissioning and refuse starts.
- Every science launch and manual/scheduled/applet backup, capture, cleanup or Drive-fetch-to-memit route uses the controller. launchd/agent jobs submitted for science must execute as the science UID and count even after the original parent exits; backup jobs similarly use the backup UID. Queued/timer/KeepAlive work must enter through the same locked mode check and cannot restart the opposing account after a clean snapshot. Direct scheduler submissions or cross-UID service delegation that bypass that fence must be unavailable; pending jobs are disabled/fenced before release, not assumed absent because their process is currently asleep or unstarted. Any permanent activity-account session/agent also blocks the opposite activity until it has exited naturally.
- Preserve existing GPU/fingerprint/dispatch refusals and their original host observation context immediately before the science payload's UID switch, under controller serialization; freeze/test actual argv, environment, tmux observation and source access rather than silently weakening admission through an account change. Use a compatible non-Python controller and keep current Python exemptions. The common mode/UID check adds the rclone backstop around the backup wrapper and actual science dispatch; existing Python classification alone is insufficient (`tools/c10w_p2_gate.py:22,51–53,73–84,151–158`). Pending science stops subsequent backup batches; finish/retain the active bounded batch, wait for the backup UID to become empty and then admit science.
- Failed/empty/malformed/partial/denied process observation, unknown credentials, stale mode, failed durable publication or lock/controller failure means RECOVERY_REQUIRED: no new science or maintenance. A valid full snapshot can contain other host users while its filtered opposing-UID set is empty; raw empty output is never absence proof. No heartbeat, timeout, root exit or Python-only scan unlocks work. Preserve existing backup generation/recovery refusal semantics (`tools/backup_gdrive_status.py:415–443`). Wait for science to finish; no forcible kill, automatic reboot or deletion clears it.
- **Reboot is RECOVERY-only**, separately operator-approved when the UID observation/enforcement boundary cannot be trusted. First preserve/checkpoint evidence or obtain explicit recovery disposition for uncertain science; reboot cannot convert interruption into PASS. After reboot, keep both activity launch routes disabled until account/privilege/scheduler bindings, complete observation, old-token fencing and reservations are revalidated. Reboot is neither a routine switch nor sufficient proof of renewed safety.

**Test:** independently enumerate a full host table and race harmless activity sentinels: only the locked selected mode launches. Retain opposing-UID Bash/orphan/launchd helpers after root exit: opposite activity must refuse until every such process ends naturally, without a descendant list. Deliver delayed/KeepAlive jobs after the absence check and after mode change: opposing-UID payloads must not launch. With opposing UID empty, fences intact and all remaining gates satisfied, both switch directions must succeed on the same boot while operator/team tmux and remote sessions remain connected. Failed/partial/denied observations, stale records, UID changes and controller death must refuse; Intel disconnection must not prevent locally valid science. Exercise fork/exit churn, disappearing PIDs, PID reuse and incomplete credential reads with an independently known surviving activity: an empty result that misses it is FAIL, and ambiguity must refuse switching; provide evidence for the chosen primitive's empty-set guarantee, not merely passing samples. Attempt file-mediated execution under the operator account by modifying group/ACL-writable trusted inputs or replacing parent-directory entries, and attempt daemon-mediated activity after its originating worker exits: both attempts must be denied or contained within the original activity UID and mode fence; execution under the operator or any unaccounted UID, or action bypassing the fence, is FAIL. Exercise every installed privilege-changing path/service available to the worker accounts: changing UID or delegating activity outside its UID is FAIL. On real M3, prove science-account Metal/MPS GPU access and the known-baseline science reproduction; unavailable GPU, silent GPU→CPU fallback, failure of the frozen baseline reproduction criteria or hidden cache recomputation is FAIL. Verify both accounts' exact memit read/write permissions, ownership/ACLs, output creation, backup readability and controller-policy protection without broad world-write grants; actual gate invocation/observation must preserve all positive/refusal controls. These commissioning science controls require separate run authorization and remain UNRUN.
**Limit:** UID completeness is conditional on exclusive account use, privilege confinement, trustworthy full-table observation and fenced future starts; a root daemon doing unaccounted activity or a bypassing scheduler is FAIL, not an account exemption. Idle GUI/agent processes may keep an account nonempty and conservatively delay the other activity. If MPS/baseline, permissions or isolation tests fail, stop for a reviewed design change; do not fall back silently to the operator account, CPU, P8 or routine reboot. No instantaneous backup preemption or forceful science termination is promised.

## R3. Proactive dynamic storage criteria S1–S12

Recorded policy requires a disk budget in every scope/prereg and free space ≥ projected writes + **20 GiB** at dispatch (`EXPERIMENT_RUNBOOK.md:275`). HW1 choice 6 records about **107 GB target / 86 GB warning**; amendment 16 leaves memit thresholds unchanged (`B/decisions_log.md:91,191`). Exact **100 GiB target / 80 GiB warning** appear in C and explain those approximate decimal values (`C:123–125`). PROPOSED retain those exact thresholds while strengthening the target into a forecast/admission floor; this semantic change is an OPERATOR DECISION in R5.

**S1 — Declare and qualify peak writes before queue admission.** Each job declares byte/count calculations and a conservative additional peak `P`, covering outputs, temporary duplication, checkpoints, logs, caches/downloads, verification and failure/retry retention across every path on memit's physical pool. Include an enforced/bounded non-science allowance `O`. Qualification covers a frozen workload/input envelope, including admitted sizes/counts, retry limits, cache states and failure paths, with justified aggregate peak bounds for every admitted case. A passing sample run is corroboration only, not an established upper bound; out-of-envelope work requires renewed qualification before admission. Unknown or unbounded growth blocks dispatch; a monitor cannot repair a missing bound. Qualification must preserve the science baseline and catch hidden cache recomputation/fallback (the ruling explicitly raises this risk: `B/r2_redesign_operator_ruling.md:5`).
**Test:** a workload with a missing frozen envelope, component or justified bound, or outside that envelope, refuses; a passing sample alone cannot qualify it. A qualified maximum-size/failure-path control corroborates the justified aggregate peak and must stay within it. Exceeding the bound fails qualification and prevents further dispatch under that budget.

**S2 — Reserve atomically at actual dispatch.** Under the activity/reservation lock, identify the physical device/pool and read current usable free bytes `F`; require `F >= P + O + R + 20 GiB`, where `R` is other reservations' remaining additional peak. Durably reserve before launching. Count existing bytes in measured use, not again as future growth; consume reservations as allocation occurs. Preserve unresolved activity commitments until the locked complete UID check proves that account empty, future starts are fenced, and its output/partial/reservation ledger is reconciled; root exit alone releases nothing. Reservations are promises backed by writer exclusion/caps in S4, not extra disk capacity.
**Test:** with other gates satisfied, just below the bound refuses, equality passes this criterion, and simultaneous requests cannot both spend the same bytes. Wrong device, missing measurement, failed persistence or an unresolved unbudgeted commitment refuses before launch.

**S3 — Protect headroom at the planned peak.** Require additionally `F - P - O - R >= 100 GiB`; below that forecast, queue the job and propose recovery before starting. Warning is actual free `<80 GiB`; the target and the separate +20-GiB rule both remain visible. Recovery operations may run below target only with their own safe budgets; they cannot borrow science's reservation or justify new science admission.
**Test:** an otherwise admissible job whose forecast ends below target refuses; exact target passes this criterion. At exactly warning threshold no low-space warning fires; below it the warning fires. Warning/target never executes deletion.

**S4 — Bound all other writers during science.** Builders, installers, Git maintenance, cache warmers, folder-size scans with writes, archive workers and housekeeping cannot make unreserved memit writes. Place support work on Intel/local permitted storage, or pause it before dispatch; internal storage never becomes a bulk archive. Permit only capped control/log writes covered by `O`. Commission protected writer permissions and actual host-supported byte caps before reliance; arbitrary same-account/admin bypass invalidates the operating boundary. Science-created helpers' writes belong to `P`, regardless of executable name. Before activation freeze aggregate allocation/reservation accounting and actual support-writer enforcement, including retained retry outputs and temporary allocate/free/reallocate cycles. Retained bytes remain charged; freeing a temporary allocation cannot release a still-needed future reallocation reservation. Neither cumulative writes nor one observed low-water allocation substitutes for the justified additional peak.
**Test:** start a builder, log burst and cache growth during the science sentinel: forbidden memit writes are denied/held, allowed writes stay inside their aggregate allowance, and the science reservation stays available. Exercise retained retries and temporary allocate/free/reallocate cycles: actual bytes plus outstanding future reservations must never undercharge the frozen peak commitments. Unsupported enforcement or an unbounded writer is FAIL, not an assumed zero budget.

**S5 — Observe dynamically without scanning the corpus.** Sample physical-pool usable free space, remaining reservations and write-rate trends during each run; PROPOSED interval **60 seconds**, to detect drift promptly with a cheap filesystem query. An observation older than that proposed interval is stale. Unknown/stale readings block new writers/jobs and show UNAVAILABLE. Alert and hold support writes on a forecast breach; no live offload, deletion or unreviewed change to science. Reuse the free-byte primitive, which reads `statvfs.f_bavail * f_frsize`; the existing display also reports measurement errors and counts shared disks once (`tools/dashboard_storage.py:141–146,328–337`).
**Test:** controlled declining free space updates forecast/warnings by the next sampling interval; a failed read cannot retain a fresh/healthy label. The collector performs no bulk traversal or maintenance during science and its actual command still passes unchanged admission rules.

**S6 — Forecast the entire admitted queue.** Recompute on every enqueue, budget/source change, completion, measured capacity change and backup outcome. Simulate ordered job peaks and retained outputs, overlapping support reservations, unfinished transfers, required upload windows and protected artifacts. Do not count proposed cleanup, deduplication or an unverified upload as reclaimed space. Publish the earliest job that would miss S2/S3, its deficit and a dated offload/cleanup proposal before admitting its predecessors when those predecessors remove the last feasible maintenance opportunity.
**Test:** a queue whose later retained growth breaches headroom produces the named deficit and a maintenance dependency before the triggering job starts. Reordering/changing budgets recomputes it; unknown queued budgets block that queue's admission, and unapproved deletions contribute no free bytes.

**S7 — Maintenance only between science jobs.** Upload/capture/hash/readback, Drive retrieval into memit and cleanup run under the dedicated backup account in R2 BACKUP mode, only after the locked complete science-UID absence check and future-start fence pass. Budget retained partials and bounded batches; leave science's next reservation intact. Schedule earlier protection for irreplaceable output and finished-data uploads between jobs, consistent with the recorded nightly/earlier-protection schedule (`B/decisions_log.md:79–81`). If a backup window cannot complete, retain partial evidence and wait/replan; never start science alongside it.
**Test:** a maintenance request while any science-UID process survives, or future science starts remain unfenced, causes no transfer/delete I/O. The same approved request succeeds in a qualified maintenance window; interrupted work retains incomplete status and cannot consume the next job's reserved capacity.

**S8 — Propose cleanup; obtain exact deletion approval.** Present paths, measured logical/allocated sizes, scientific holds, rebuildability, retained samples, Git hashes and verified archive evidence. Every deletion needs explicit operator approval of the exact paths, size and method; no threshold or retention expiry grants it. Runbook §3.3 has historical standing-reclaim wording, while §3.3a classifies retention/archive obligations; this redesign follows the task's stricter explicit-approval rule (`EXPERIMENT_RUNBOOK.md:259–278`).
**Test:** low space, an expired cache or a completed upload without exact approval causes no deletion. An approved deletion still refuses during science or on changed identity/hold; after permitted execution, only measured reclaimed bytes reduce the forecast deficit.

**S9 — Verify irreplaceable offload before counting protection.** Preserve local originals until remote whole-content verification, path/metadata coverage and SHA-256/size receipts are committed to Git. Distinguish copy completion from permission to remove the source. Irreplaceable bulk's Drive tier is recorded policy (`EXPERIMENT_RUNBOOK.md:274`).
**Test:** remote missing/altered/partial bytes, incomplete coverage or absent Git receipt leaves bulk unprotected and local originals retained; a fully verified committed generation becomes protected, but remains undeletable without S8 approval.

**S10 — Forecast archive capacity and upload time too.** Measure current Drive capacity and reserved/history/partial growth before uploads; estimate transfer duration from observed host throughput, approved bandwidth and required readback. Queue maintenance early enough for actual windows; unavailable Drive/quota/bandwidth blocks reliance on planned offload. Historical upload speed and first-copy duration are dated planning evidence, not promises (`EXPERIMENT_RUNBOOK.md:277`).
**Test:** a forecast exceeding current remote capacity or available maintenance time holds the dependent science queue and emits the deficit/action proposal; increasing assumed bandwidth or treating historical free space as live capacity cannot make it pass.

**S11 — Revalidate after maintenance/restart/remount.** Match physical identity, committed manifests, actual free bytes and retained partials; reject stale reservations/old epoch tokens. Reconcile conservatively rather than resetting unknown use to zero. Routine mode switches require locked UID absence/future-start checks and ledger reconciliation without reboot. Controller restart or RECOVERY reboot permits neither mode until R2 account/privilege/observation checks pass; it does not itself qualify data or space.
**Test:** a routine switch or restart/remount with a surviving opposing-UID process, unfenced future start, changed device, stale token, lost ledger or unaccounted partial refuses dispatch until full UID observations and surviving commitments reconcile; no duplicate physical pool is counted as new capacity.

**S12 — Commission the prevention claim, not just alerts.** Prove the S1–S11 admission/enforcement chain on real M3 storage with bounded harmless writes, concurrent support attempts, failed measurements and interrupted maintenance. An accepted maximum-bound run must finish with protected headroom; monitor-triggered science termination is FAIL. No promise of disk-full immunity for unbounded workloads, unauthorized privileged writes or hardware faults: those are outside qualified operation. Design adoption may approve these conditional requirements; activation and operational acceptance remain OPEN until enforcement is demonstrated.
**Test:** the maximum declared job plus maximum allowed support growth completes without disk-full, quota-induced science stop, live offload or live cleanup; all rejected workloads never start. Fixtures alone cannot qualify this claim.
