# Web dashboard integration review — 2026-10-11

## 1. Summary for the operator

- Keep the existing static LabViz as the base; its recorded-file approach already matches the evidence rules. (`results/dashboard_integration_review_20261011/CONTEXT.md:10,15`)
- [ECharts](https://github.com/apache/echarts) is worth a later trial for interactive science charts, without adding an application server.
- [Tabler](https://github.com/tabler/tabler) is worth a later, small layout trial for the phone page; use local assets and avoid its bundled chart plugins.
- [Altair](https://github.com/vega/altair) is worth a later trial for reproducible chart exports; Python runs during generation, not while viewing.
- [Perspective](https://github.com/perspective-dev/perspective) merits a trial only if filtering and comparing many runs becomes awkward; its browser engine adds packaging work.
- [Aim](https://github.com/aimhubio/aim) offers useful run-comparison ideas, but a new tracker store and UI service duplicate part of LabViz rather than solve the frozen-status phone page. (`results/dashboard_integration_review_20261011/CONTEXT.md:15,16`)
- Skip the full application and BI platforms for this scope: they introduce service operations or substantial frontend machinery; see their opened sources and costs below.
- Nothing here authorizes building or installing anything; the operator's hold remains in force. (`results/dashboard_integration_review_20261011/CONTEXT.md:4`)

## 2. Item-by-item assessment

**Reading boundary:** each project was skimmed through its repository README and one release page, without installing or executing it. Integration paths, weight labels and verdicts are this review's assessment, not tested capabilities of our deployment.
**Release/maintenance boundary:** the tags below were labelled Latest on the opened pages. Most dates displayed only day/month; those are transcribed without inventing a year. A release is evidence of a release line, not proof of current support or security maintenance; continuing maintainer activity was not audited. Charts.css supplies a year in its release title.
**Weight:** low = browser assets; medium = frontend/build or export dependencies; high = application service plus its environment/data store. These are comparative estimates; no install sizes were measured.
**Repo anchors used in every integration cell:** B = current file-URL LabViz, vanilla JS and SVG/Pillow renderer (`results/dashboard_integration_review_20261011/CONTEXT.md:15`); C = proposed Intel phone page reading one frozen status record (`results/dashboard_integration_review_20261011/CONTEXT.md:16`); records = JSON/JSONL, Markdown and logs (`results/dashboard_integration_review_20261011/CONTEXT.md:11`). No item is proposed as an A terminal replacement or D skill install (`results/dashboard_integration_review_20261011/CONTEXT.md:14,17`).
**Evidence contract for every candidate:** our adapter must carry source path, recorded timestamp, units and any denominator; absent values stay missing, never zero. C must expire the displayed record using its source timestamp, including while the page remains open; network failure must not turn cached data into OK. A fresh page load is not a fresh source. These are proposed enforcement points for the existing rule, not framework guarantees (`results/dashboard_integration_review_20261011/CONTEXT.md:10,16`).
**Privacy and GPU shorthand:** LOCAL = the proposed deployment uses local assets/data and no external connectors/accounts; this is not a telemetry audit. CDN assets, external fonts and optional cloud integrations are separate egress risks. JS = no new host Python process; BUILD = Python generation must be scheduled around admission; SERVICE = a non-exempt Python service on the science Mac would block admission, so any such evaluation belongs on Intel, with host isolation still to verify (`results/dashboard_integration_review_20261011/CONTEXT.md:7,14`). Browser rendering still consumes memory; JS does not mean resource-free.
**Static distinction:** B should receive embedded data/local classic-script assets rather than rely on fetching adjacent JSONL files. C still needs a maintained HTTP hosting/access arrangement, even for static assets; these libraries do not provision it. File-URL and iPhone compatibility remain untested. TRIAL means a candidate for consideration after the hold, not approval to start.

**Aim against the actual workflow:** the records are files, not a mandatory tracking SDK stream (`results/dashboard_integration_review_20261011/CONTEXT.md:11`). Aim's [README](https://github.com/aimhubio/aim) documents SDK logging, converters for named trackers and custom conversions. An integration would therefore require our own mapping, not just pointing Aim at `results/`.
Proposed mapping: carry a stable source identity/path/hash; copy parameters and scalar metrics only where recorded; preserve model/variant, metric unit, denominator and context. Import histories only when steps/timestamps exist; a final scalar must not become an invented training curve. Markdown verdicts and HALT/acceptance labels remain explicit source-linked fields, independent of Aim's run lifecycle. This follows the missing/source rule (`results/dashboard_integration_review_20261011/CONTEXT.md:10,11`); the [release's stalled-to-finished behavior](https://github.com/aimhubio/aim/releases/tag/v3.29.1) is a concrete reason to retain that separation.
Before reconsidering Aim, a later disposable importer would need to reproduce selected original values/denominators, reject duplicate source imports, expose missing histories, preserve HALT and stale status, and leave every original file unchanged. That is a proposed proof obligation, not work started. Its benefit must exceed what B's existing Runs/Science views already provide (`results/dashboard_integration_review_20261011/CONTEXT.md:15`).

## 3. Top three recommendations

All steps below are **future proposals after the operator lifts the hold**, not a recommendation to begin now (`results/dashboard_integration_review_20261011/CONTEXT.md:4`). Common proposed acceptance: source-linked values match the original files; missing is visible; no research-data upload; C expires stale data and fails closed on malformed/missing records. No live experiment or GPU process is needed for a UI trial.

1. **ECharts: one interactive science chart.** [Basis](https://github.com/apache/echarts): browser JavaScript charting with distributable assets. First reversible step: a disposable comparison page for one existing B science-line chart, with pinned local assets and embedded data. Worth it if file-URL opening works without network, every plotted point matches its cited record, nulls remain gaps, and the chart stays readable/usable at 390 px width. Proposed budget: at most 250 KB additional compressed chart assets for this single chart; measure rather than assume. Displaces that chart's renderer only; duplicates B's existing SVG/Pillow output during comparison, not its parser or five-view structure (`results/dashboard_integration_review_20261011/CONTEXT.md:15`).
2. **Tabler: one phone status layout.** [Basis](https://github.com/tabler/tabler): compiled HTML/CSS/JS kit; [release](https://github.com/tabler/tabler/releases/tag/@tabler/core@1.6.1). First reversible step: an isolated status-card mockup using local core CSS and copies of a fresh, expired and missing frozen record. Worth it if the operator can read status/source age at 390 px without horizontal scrolling, keyboard navigation works, there are zero third-party asset requests, and an open page changes to UNAVAILABLE when the source expires. Check the actual phone against the README's Safari requirement. Would supply C's visual shell, duplicating handwritten layout CSS; C itself remains unbuilt, so nothing deployed is displaced (`results/dashboard_integration_review_20261011/CONTEXT.md:16`).
3. **Altair: one deterministic chart export.** [Basis](https://github.com/vega/altair): JSON specifications and standalone HTML/SVG export. First reversible step: generate one comparison chart from a copied, frozen record set in a disposable export environment, then end the Python process. Worth it if two exports from identical inputs have identical chart specifications, recorded values/units/denominators match, missing measurements remain labelled, and the HTML opens by file URL with the network unavailable. Exported HTML must carry its assets/data locally; unsupported interactions fail this trial. Would replace selected B SVG/Pillow chart definitions and add an export dependency; it duplicates ECharts' chart role, so choose by the result rather than adopt both automatically (`results/dashboard_integration_review_20261011/CONTEXT.md:15`).

## 4. Ideas worth borrowing

- [Aim](https://github.com/aimhubio/aim): compare runs by explicit parameter/context filters; retain links back to recorded evidence.
- [Redash](https://github.com/getredash/redash): show the data selection/query behind each chart; retain refresh timestamps beside it.
- [Refine](https://github.com/refinedev/refine): separate read-only data acquisition from layout; suppress all mutation controls for these surfaces.
- [Superset](https://github.com/apache/superset): define reusable metric units/denominators once in the adapter instead of independently in each chart.
- [Panel](https://github.com/holoviz/panel): export-first reports and linked views; assess export interaction limits before adopting a service.
- [Gentelella](https://github.com/ColorlibHQ/gentelella) / [CoreUI](https://github.com/coreui/coreui-free-bootstrap-admin-template): compact health cards, narrow-screen navigation and clear focus states without migrating the whole template.
