Intel shall serve the operator's phone and local views from the same validated record set. The three views are M3 science/MAESTRO, Intel builders/research engine, and storage/copy/restore. Existing local ps/tmux/file readers cannot simply move to Intel and still observe M3 (`B/design.md:267–269`).

## 2. Record fields and payload

Each source shall publish one UTF-8 JSON record with these exact top-level fields. Reject unknown/missing fields, duplicate JSON keys, non-finite numbers, wrong types and unknown schema versions. Integers exclude booleans; timestamps are ISO-8601 UTC with `Z`; IDs are nonempty strings with no control characters; UUID fields use canonical lowercase UUID syntax; hashes are lowercase 64-hex strings. These are v1 schema choices implementing the identity requirement (`B/astra_r1_verdict.md:28`).

| Field | Frozen meaning |
|---|---|
| `schema_version` | Integer `1`. |
| `source_host` | Object: `role` exactly `m3` or `intel`, commissioned `host_id` UUID, human `label`, commissioned `platform` string, current `boot_id` UUID. The reader's reviewed host registry maps role/host/key/platform; a label is never authentication. |
| `collector` | Object: fresh `generation_id` UUID per process start/reexec, positive `pid`, UTC `started_at`, `source_sha256` and `profile_sha256`. A PID alone never identifies an incarnation. |
| `sequence` | Positive integer, strictly increasing within one collector generation; increment only on a newly published record. |
| `source_observed_at` | Earliest successful observation time among CURRENT components in this record; null if none. It does not date failed attempts or cached evidence. Component timestamps below control their own age. |
| `writer_at` | UTC time after collection and serialization, immediately before publication. Copying/serving a record shall not change it. |
| `views` | Object with exactly `m3_science_maestro`, `intel_support`, `storage_transfers`; each is the component map below. A source's non-owned view is exactly `{"state":"NOT_OWNED"}`; it cannot supply an empty substitute payload. |

Each owned view is exactly `{"state":"OWNED","components":{...}}`. Component names are fixed below. Each component is one of three forms: CURRENT (`state`, `observed_at`, `payload`, `provenance`); LAST_KNOWN (the same fields plus nonempty `reason`); UNAVAILABLE (`state`, null `observed_at`, nonempty `reason`, null `payload`, empty `provenance`). CURRENT means collection succeeded, not that a later reader must accept it as fresh. LAST_KNOWN retains the original successful timestamp and payload; a new writer time cannot freshen it. A view with some failed components shall show those components as UNAVAILABLE, never infer a fully idle view from the others.

Every provenance entry has `kind` (`file`, `process_inventory`, or `session_inventory`), source `host_id`/`boot_id`, `observed_at`, and identity: file absolute path plus content SHA-256, or observer command plus observation sequence. Paths identify sources, not remote read instructions. Readers shall never follow arbitrary paths from a received record. Nested file/artifact measurement times remain distinct from collector read times.

## 4. Named freshness and disconnected behavior

These values are frozen v1 acceptance parameters, not measured performance or clearance deadlines. They implement the required age/loss semantics (`B/astra_r1_verdict.md:28`; `B/design.md:267`).

| Name | Value / use |
|---|---|

| `M3_POLL_INTERVAL_S` | 5 seconds, one outstanding Intel request, no retry burst. |
| `PANE_OBSERVE_INTERVAL_S` | 15 seconds for session roster; preserve the existing screen-cache minimum interval (`tools/dashboard_live.py:605,623–631`). |
| `TRANSPORT_DEADLINE_S` | 2 seconds total connect/read deadline per request. |
| `COMPONENT_PROBE_DEADLINE_S` | 2 seconds per native inventory; failure affects its dependent components. The current queue command boundary also has a two-second timeout (`tools/dashboard_queue.py:455–456`). |
| `M3_LIVE_STALE_S` | 30 seconds: M3 science/MAESTRO live observations. |
| `INTEL_LIVE_STALE_S` | 30 seconds: builders/RE health/resource observations. |
| `CLIENT_FEED_STALE_S` | 30 seconds: last successful Intel-service response at each phone/local client; poll every 5 seconds with a 2-second deadline. |
| `TRANSFER_LIVE_STALE_S` | 30 seconds per source: transfer/restore stage and warnings. |
| `DISK_SPACE_STALE_S` | 30 seconds: free/used measurements. |
| `FOLDER_SIZE_STALE_S` | 1,800 seconds: original completed folder measurement. Keep the existing 900-second scan throttle (`tools/dashboard_storage.py:24,262–270`). |
| `MAX_CLOCK_ERROR_S` | 2 seconds: maximum verified source/receiver UTC uncertainty; larger/unknown uncertainty makes cross-host currentness UNAVAILABLE. |

At receipt, conservatively calculate age from original `observed_at` using verified clock uncertainty; anchor that age to Intel's monotonic clock. Later age is at least anchored age plus monotonic elapsed time. Duplicate reads, cached redraws, new heartbeat/writer times and backward wall-clock jumps cannot reduce it. Negative/future times beyond `MAX_CLOCK_ERROR_S`, observation after writer time, or writer time before collector start reject the record. Suspend/resume or clock-discontinuity uncertainty requires live revalidation. CURRENT requires age <= the relevant threshold; age > threshold is UNAVAILABLE/stale. LAST_KNOWN is historical even inside the threshold. Source timestamps of older source generations/measurement caches always remain visible separately.

M3 view: the first failed/invalid transport observation marks M3 current status UNAVAILABLE/disconnected immediately, with last-seen time and advancing age; do not wait for the stale threshold after known connection failure. Preserve last-known run/task identities and critical decisions as dated context. Recovery requires a complete fresh validated record, not an empty successful HTTP body.

Intel view: continue independently through M3 loss. Failed Intel-local inventory or stale Intel observations affect Intel components, not M3 attribution. A research query's dated immutable source generation may remain usable under its coverage rules even when its dashboard health feed is unavailable (`B/design.md:233,235`). Dashboard freshness is not database source-age acceptance.

Phone/local client loss of the Intel service shall mark the service feed and all current observations UNAVAILABLE at the first failed request, retaining last source times/ages as historical context. A cached page continues advancing ages; it cannot remain CURRENT beyond `CLIENT_FEED_STALE_S`. Client-local ps/tmux cannot substitute for a lost service. A client with no valid clock/receive anchor shows `age unknown` and UNAVAILABLE. This applies the same lost-observation meaning at both clients (`B/design.md:267–269`).

Transfers view: render Intel-local uploads from verified local checkpoints independently; M3/memit source, coordinator and clearance observations become UNAVAILABLE on M3 loss. Retain warnings, cap exhaustion, incomplete coverage, operator decisions and checkpoints. Never turn disconnected transfer state into completed, paused, idle or clearance. A dated R2 summary cannot grant/resume work (`B/design.md:235,259,265,267`; `B/astra_r1_verdict.md:24`).

## 5. Small transport and resource limits

Select a fixed read-only HTTP snapshot endpoint inside the one M3 collector process, bound only to the commissioned private Thunderbolt IP on port 8766. Intel polls only `GET /status/v1`. The signed envelope supplies source authentication/integrity; the private link is the transport restriction. Do not bind `0.0.0.0`, expose files, execute requests or launch remote commands. Concrete IP/route and per-host secret references belong in the reviewed identity profile; interface commissioning remains due because the design requires the chosen private cable interface to be demonstrated (`B/design.md:208,269`). This is one fixed byte stream, not shared-filesystem mirroring or a new Python worker pool.

The listener shall read only the committed local cache; handlers cannot trigger ps/tmux/file collection. One in-process collector and at most one in-process responder thread, no child HTTP server, no `--gpu-summary` poll, no Python subprocess/import that loads torch, a model or embedding runtime. A stalled Intel client shall not stall collection; bound handler time to `TRANSPORT_DEADLINE_S`. The collector continues without an Intel client and science does not consult the endpoint (`B/design.md:216,269`).

Frozen limits: `MAX_ENVELOPE_BYTES=262144`, `MAX_RECORD_BYTES=196608`, one outstanding request, no unbounded receive/history buffer; exceed a size bound → UNAVAILABLE/oversize, never truncate a run or warning silently. Polling consumes at most 262144 bytes per five seconds per source, excluding protocol overhead. Proposed M3 collector RSS ceiling 64 MiB; Intel dashboard/collector/receiver aggregate ceiling 256 MiB, included within the existing <=6 GB support target, not added on top. The <=3 GB RE aggregate, <=2 GB Neo4j, one builder job, practical >=6 GB OS/user allowance and background priority >=10 stay intact (`B/design.md:218,237`). Use process niceness in process; no shell priority wrapper. Exceeding/unknown resource observations pauses new heavy Intel support admission under the existing design, never M3 science. These are commissioning targets, not measured enforcement.
