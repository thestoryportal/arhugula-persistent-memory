**Rule.**
1. **Cardinality follows pinned code, not the eventual validator.** Each recorded process site states what bounds its occurrence count before the spawn: `pinned_constant` (cite the enforcing line, e.g. the loop at :515) or `loaded_data` (no pinned pre-spawn bound). A validator that runs after the spawns (such as `validate_phase` at :551 / :333) is not a bound for those spawns. Neither is a constant that the code compares against only after them (`TRAIN_UNITS` for route V).
2. **Operand values follow pinned code too.** Each site records its operand source: `pinned_literal` (cite the line) or `loaded_data` (cite the record and field it is read from, plus every pinned pre-spawn constraint on it, e.g. ROOT containment at :132 and the `--` separator at :133). Two occurrences share a bound recipe only when pinned code reached before both spawns establishes that their executable, argument structure **and** operand values are equal. The same executable and command shape alone does not make them the same recipe. This refines D14 item 2: "the same Git recipe" means equal bound operands, not equal shape.
3. **Route V (verifier → `replication_for`) is a `loaded_data` operand family with `loaded_data` cardinality.** For every admission that reaches it (each P2 stage except the first, and `p2-eval`, per D14 item 2), record one ADMISSION_HELPER / C:115 operand-family occurrence: executable and argument structure pinned at :133, operand source `eval.json → train_records[*].adapter.path` (:543, :549–550), constraints :132–133, count unbounded before the spawn. Do not represent it as six (or any fixed number of) bound recipes.
4. **Route T (gate `p2-eval` → `phase_trains`) stays separate.** Record it as its own ADMISSION_HELPER / C:115 occurrence: count `pinned_constant` (at most six, :515), operand source `train/<tag>_{400,800}.json → adapter.path`, selected by file existence (:516–520), constraints :132–133. Profile 38 therefore has two admission-origin Git occurrences with distinct operand sources. Never merge them, and never merge either with a science-origin occurrence (D13 item 1).
5. **Uncoverable cases are refused, explicitly.** C:115 requires every permitted invocation to be enumerated. A `loaded_data` cardinality cannot be enumerated, so every admission or composition that reaches such an occurrence is refused. It keeps `NOT_ADMITTED_ADMISSION_HELPER_UNREGISTERED:` (D10) and adds `NOT_ADMITTED_OPERAND_DOMAIN_UNENUMERATED:` naming the site. Refusal reasons are only ever added (D14 item 6). The freeze must not claim that any count, including six, bounds route V.
6. **Apply items 1–2 to every recorded process site, both origins.** For each site, record its count kind and operand source. A1 is not widened: when a science-origin occurrence's count or operands are `loaded_data` beyond what A1 enumerates, refuse the uncovered part with the item 5 reason and do not stretch A1 to cover it. The report states how many sites of each kind there are, per origin.
