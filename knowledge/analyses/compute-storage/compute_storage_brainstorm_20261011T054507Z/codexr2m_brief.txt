== Design decisions already made (MAESTRO) ==
R2, science launch ID (V5 F2): add an immutable ScienceLaunchContextRecord, modelled on RecoveryLaunchContextRecord: schema "R2-v1", record_type, context_id, launch_id, host_id, boot_id, launch_profile_sha256 (the unrendered LaunchProfile H; no cycle, because H never covers rendered values), values (an object whose keys are binding names and whose values are nonempty strings; its key set must equal exactly the owning profile's declared names whose source_field starts with /values/), created_elapsed, created_utc, context_mac. The science launcher exclusive-creates it before spawning the guard; choose its path under R and its authentication from F3's existing rules for immutable source records, citing the C clause. The science-guard template keeps {"$bind":"launch_id"}, declared as source_record ScienceLaunchContextRecord, source_field /launch_id. Make F4's §2 entrypoint table, the §4 binding-source rule, the J3 declarations, the context-record example, the InvocationBinding example and its rendered argv agree; the science InvocationBinding example names the context record's hash as the launch_id source, and no template example carries a literal launch ID.
Profile shapes (codexr2n writes against these; keep them otherwise unchanged): (a) BindingDeclaration.source_record admits "ScienceLaunchContextRecord"; (b) InvocationProfile gains a required field `dependencies`: an array (0–256 items) of a new DependencyIdentity {path: Path, sha256: Hash}, additionalProperties false. Add `dependencies` to every existing InvocationProfile instance in J3 (an empty array is acceptable only where the executable has no separate dependency file) and recompute what that changes; (c) EnvironmentEntry.value admits BindingPlaceholder as well as a literal string (a science child's environment can carry a bound run directory), rendered by the same rule as argv, and InvocationBinding gains rendered_environment (sorted name/value pairs) and rendered_environment_sha256, which consumers check with the argv.
R3, observation revision (V5 F3): an ObservationRecord's epoch, sequence, ledger generation and pending launch ID are the committed authority revision it observed BEFORE the commit. Rename those fields so the meaning is unambiguous (for example observed_authority_epoch, observed_sequence). Under authority.lock the coordinator compares the current committed revision with them; any difference requires fresh proof (F3:220 otherwise unchanged). The commit produces resulting sequence = observed_sequence + 1 in the same epoch, recorded separately in the decision and the new AuthorityRecord; an observation never names the revision its own commit creates. Fix the J2 construction V5 F3 cites (J2:15714–15725, 15843–15854, 14221–14238, 11903–11908) so the clearance observation names the pending revision it observed and the decision names the resulting one. RECONCILE approval (V5 R3; K2:755–767): MaestroApprovalReceipt names the observed old (epoch, sequence) in its observed fields and the replacement in a separate proposed_epoch field; the result is (proposed_epoch, sequence 1) per J2:28181. No field ever pairs an epoch from one revision with a sequence from another. Add one table to F4 (in §4 or §5) listing, for every request kind that commits, the precommit revision it checks, any intermediate publication (REGISTER_SCIENCE's PENDING) and the resulting revision, each with its C clause.
Construction coherence (enables V5 R4 in the later checker): add to J3 `x-construction.mandatory_hash_fields`: for each schema with fields that hold another record's hash, the list of JSON Pointers to those fields, taken from F4 §4's "X = Y hash" statements (cite the F4 line per schema). Every example must then have a hash_references entry for each such field it carries. Every InvocationBinding example's source_field must resolve in the example of the record it names, and its rendered argv must equal the template with exactly those values substituted.
