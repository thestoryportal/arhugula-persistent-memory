## 2. Complete closed wire grammar — R1/F1

### 2.1 Notation, primitive types and universal presence rules

The following is a type grammar for JSON, not executable code. `Type {field: Type,...}` lists EVERY field of that object. Every listed field is REQUIRED; every unlisted field is FORBIDDEN, at every depth. A union selects exactly one form by its discriminator; fields of other forms MUST be absent. No implicit optional fields, defaults, coercions or extensions exist. Constant quoted strings and enumerations are JSON strings with exactly the listed vocabulary. Duplicate keys, non-finite numbers, malformed UTF-8 and unknown versions are rejected. Integers exclude booleans. Validate raw JSON keys before constructing objects.

| Type | JSON type and allowed values | Null / empty semantics |
|---|---|---|
| `Bool` | boolean, `true` or `false` | null/string/list forbidden |
| `UInt` / `Pos` | integer 0..9007199254740991 / 1..9007199254740991 | null/string/list forbidden; 0 is a measured zero only for UInt |
| `Percent` | integer 0..100 | null forbidden unless `Percent?`; zero means parsed 0% |
| `ID` | string, 1..128 characters, no C0/DEL controls, non-whitespace | null, empty string/list forbidden |
| `Text` | string, 1..4096 characters, no C0/DEL controls, non-whitespace | null, empty string/list forbidden |
| `Words` | string, 0..4096 characters, no C0/DEL controls | empty means an explicitly empty recorded text; null/list forbidden |
| `Command` | string, 1..8192 characters, no C0/DEL controls | null, empty string/list forbidden |
| `Path` | string, absolute POSIX path, 1..4096 characters, no C0/DEL controls | null, empty string/list forbidden; never a reader instruction |
| `UUID` | string, canonical lowercase `8-4-4-4-12` hexadecimal UUID | null, empty string/list forbidden |
| `Hash` | string, exactly 64 lowercase hexadecimal characters | null, empty string/list forbidden |
| `UTC` | string, real UTC date/time exactly `YYYY-MM-DDTHH:mm:ss.sssZ`, seconds 00..59 | null, empty string/list forbidden |
| `SessionName` | string, 1..128 characters, no C0/DEL controls, no colon, non-whitespace | null, empty string/list forbidden; passed as ONE argv element, never shell-expanded |
| `T?` | the stated type T OR JSON null, only where explicitly written | null has the field-specific meaning below; empty is still subject to T's rules |
| `List<T>` / `Nonempty<T>` | JSON array, 0..1024 / 1..1024 entries of T | null/string forbidden; List empty semantics enumerated below; Nonempty empty forbidden |

Objects cannot be null, strings or lists unless an explicit union says so. Empty objects are forbidden: even NOT_OWNED contains its discriminator. Constant `null`, `[]`, `true` and `false` are the exact JSON value and type, not optional placeholders. IDs within each list are unique; dependencies refer to existing queue item IDs and contain no cycle. An envelope cap bounds total nesting/data; reject nesting deeper than 32 JSON container levels as BAD_VALUE rather than accepting partial data.

### 2.2 Envelope, record, ownership and components

`Envelope {envelope_version: 1, record_utf8_b64: Base64, hmac_sha256: Hash}`. Base64 is a nonempty JSON string of canonical padded RFC-4648 standard-alphabet base64, no whitespace; decoded bytes must be nonempty UTF-8 JSON. Null, empty string/list, URL alphabet and noncanonical padding are forbidden. HMAC-SHA256 covers exact decoded bytes with the commissioned per-source key. No pane text, secrets, transcripts or credentials go on the wire. Serving/copying cannot resign or change those bytes (`B/dashboard_host_status_record_v1.md:45,84–86`).

`Record {schema_version: 2, source_host: Host, collector: Collector, sequence: Pos, source_observed_at: UTC?, writer_at: UTC, views: Views}`. sequence strictly increases only on newly committed publication within this incarnation; writer_at is sampled after collection/record preparation immediately before final serialization/publication, never at serving/copying. PID alone never identifies an incarnation (`B/dashboard_host_status_record_v1.md:23–26`).
`Host {role: "m3"|"intel", host_id: UUID, label: Text, platform: "macos-arm64"|"macos-x86_64", boot_id: UUID}`; role/platform pair is m3/macos-arm64 or intel/macos-x86_64 and must match the commissioned registry. Label is display only.
`Collector {generation_id: UUID, generation_number: Pos, pid: Pos, started_at: UTC, source_sha256: Hash, profile_sha256: Hash}`; generation_number is host-wide, survives boots, and is never a PID or timestamp order (§3).
`Views {m3_science_maestro: M3View, intel_support: IntelView, storage_transfers: StorageView}`.
`NotOwned {state: "NOT_OWNED"}`; no components/payload/reason field. m3 owns M3View and StorageView; intel owns IntelView and StorageView. Its other view MUST be NotOwned. An owned view cannot be replaced by NotOwned or an empty payload.
`M3View = NotOwned | {state: "OWNED", components: {science: Component<Science>, maestro: Component<Maestro>, queue: Component<Queue>}}`.
`IntelView = NotOwned | {state: "OWNED", components: {builders: Component<Builders>, research_engine: Component<ResearchEngine>, resources: Component<Resources>}}`.
`StorageView {state: "OWNED", components: {disks: Component<Disks>, folder_sizes: Component<Folders>, transfers: Component<Transfers>, warnings: Component<Warnings>}}`.
`Component<T> = {state: "CURRENT", observed_at: UTC, payload: T, provenance: Nonempty<Provenance>} | {state: "LAST_KNOWN", observed_at: UTC, payload: T, provenance: Nonempty<Provenance>, reason: Text} | {state: "UNAVAILABLE", observed_at: null, payload: null, provenance: [], reason: Text}`.

CURRENT means successful collection, subject to reader freshness. LAST_KNOWN retains the original payload/time and is historical even inside the threshold. Its source provenance must belong to the same enclosing collector generation: across reexec the reader retains older-generation data as historical context outside the new record, never relabels old provenance as new. UNAVAILABLE means no successful payload supplied; the literal nulls/empty provenance are required and do not mean idle. `source_observed_at` is the minimum observed_at of all CURRENT owned components, exactly; null iff none. This null is permitted only there, not an empty time string. Partial collection failure affects that component and dependent claims, never invents a fully idle view (`B/dashboard_host_status_record_v1.md:25,29,49`).

### 2.3 Provenance, subject and original receipts

`Subject {kind: "RUN"|"TASK"|"SESSION"|"TRANSFER"|"RE_PUBLICATION"|"R2", id: ID, generation_id: UUID, host_id: UUID, boot_id: UUID}`. This is the original source subject generation, NEVER substituted by collector generation. `Origin {role: "m3"|"intel", host_id: UUID, boot_id: UUID, collector_generation_id: UUID, collector_generation_number: Pos}` represents a dated observing incarnation.
`Provenance = {kind: "file", host_id: UUID, boot_id: UUID, collector_generation_id: UUID, collector_generation_number: Pos, observed_at: UTC, subject: Subject?, path: Path, sha256: Hash} | {kind: "process_inventory"|"session_inventory"|"pane_capture", host_id: UUID, boot_id: UUID, collector_generation_id: UUID, collector_generation_number: Pos, observed_at: UTC, subject: Subject?, command: Command, observation_sequence: Pos}`.
`Receipt {path: Path, sha256: Hash, measured_at: UTC, subject: Subject}`; no optional/null/empty fields. A receipt is a pointer and hash of saved original evidence, not content verification by the dashboard. Reader NEVER follows received paths.

Every provenance host_id/boot_id/collector tuple must equal the enclosing Record's tuple, including generation_number. Its observed_at must equal the component's observed_at: multi-probe observations use the earliest successful capture time as their common batch stamp, only after every required probe succeeds. A subject, when non-null, must match an actual subject in that payload in kind/id/generation/host/boot. Null means host-level inventory/file observation, not unknown run identity. Every identified run/task/transfer and RE publication requires a matching non-null file subject provenance entry from its authority source; inventory-only provenance cannot establish original job identity. Asserted live processes also require local process_inventory; BUSY/WAITING/IDLE require session_inventory and pane_capture at the same batch stamp. MISSING needs successful session inventory, not a fictitious successful capture; UNAVAILABLE must not cite a failed capture as successful provenance. Repeated session identity at the same observation time across components must agree on process/activity. Provenance mismatch in any part rejects the record as PROVENANCE_MISMATCH.

Each Receipt.subject must equal its containing evidence owner's Subject, except a transfer's source_manifest, whose subject equals source_subject. Receipt.measured_at is original evidence time, no later than that component's observed_at; never renewed by transport. An Origin referring to a remote transfer endpoint is explicitly dated remote evidence, checked against the registry and its own job subject, not falsely equated to local envelope provenance. An unavailable identity cannot have a live process or matching-current provenance claim (`B/dashboard_host_status_record_v1.md:31,35–39`).

### 2.7 Deterministic reader outcomes and example contract

ACCEPT means a validated record is admitted with its component states, NOT that LAST_KNOWN/UNAVAILABLE becomes current. Entire-record refusal shows UNAVAILABLE and a reason code; retained data is historical with advancing age. A component freshness failure shows that component UNAVAILABLE/STALE_COMPONENT, retaining original source time/age; other valid components remain independently attributed. Do not update its last-success time. No rule silently truncates data or substitutes idle/zero/completed.

Validation order and first-failure codes: transport failed/no response → TRANSPORT_FAILURE (successful empty body goes to BAD_JSON); bytes >MAX_ENVELOPE_BYTES → OVERSIZE_ENVELOPE; malformed envelope JSON/UTF-8 → BAD_JSON; duplicate keys → DUPLICATE_KEY; envelope unknown/missing/type/constant checks → UNKNOWN_FIELD/MISSING_FIELD/WRONG_TYPE/UNKNOWN_VERSION; base64 → BAD_BASE64; decoded cap → OVERSIZE_RECORD; record JSON → BAD_JSON/DUPLICATE_KEY; signature → BAD_SIGNATURE; record grammar → UNKNOWN_VERSION/UNKNOWN_FIELD/MISSING_FIELD/WRONG_TYPE/BAD_VALUE/OUT_OF_VOCABULARY/CONDITIONAL_FIELD (in that precedence, ties by lexicographic JSON Pointer); registry/hash ownership → IDENTITY_MISMATCH; metadata validation → READER_STATE_MISSING/READER_STATE_CORRUPT/TRANSITION_UNVERIFIED; generation and sequence → OLD_GENERATION/TRANSITION_UNVERIFIED/GENERATION_CONFLICT/SEQUENCE_REGRESSION/SEQUENCE_CONFLICT; provenance/semantic relationships → PROVENANCE_MISMATCH/SEMANTIC_INVALID; clock → CLOCK_UNVERIFIED/BAD_TIME; freshness → STALE_COMPONENT. Missing/present union-only fields use CONDITIONAL_FIELD, not MISSING_FIELD/UNKNOWN_FIELD. Null in a nonnullable field, non-null in a null-only field, or a non-list in a literal [] field is WRONG_TYPE. Empty nonempty-type strings/lists or nonempty literal-[] lists are BAD_VALUE. Envelope HMAC authenticates bytes before their record fields are USED, even though JSON syntax may be inspected first. A no-input reader with absent/corrupt metadata is immediately UNAVAILABLE/state reason without waiting for a poll.

`B/dashboard_record_v2_examples.json` supplies literal base records, literal signed base envelopes, an explicitly public fixture-only key, trusted reader contexts and deterministic input-edit recipes. Record edits are made BEFORE canonical serialization/signing; thus grammar cases are correctly signed. Envelope/raw-byte cases are made AFTER signing. Edits are sequential JSON Pointer operations, never implementation-dependent merge behavior. Its predetermined outcomes are frozen before any reader exists. The fixture context's UTC/uncertainty and durable pin/state are part of each case; no fixture is a live host receipt. Oversize recipes specify exact bytes without storing a huge literal.

### 3.1 Generation order and independently verified current transition

HMAC authenticates stored bytes; it does NOT prove a live endpoint or current process. Replace v1's automatic authenticated-live-endpoint generation admission: a snapshot alone can NEVER introduce a boot/generation, even if signed/fresh (`B/astra_r4d_verdict.md:9,15`; `B/dashboard_host_status_record_v1.md:51`). The selected minimal mechanism is a commissioned, out-of-band current-generation pin. This intentionally requires dashboard-only revalidation on collector boot/reexec; it does not make science wait.

Source counter: `Counter {version: 1, host_id: UUID, last_reserved_generation: UInt}` in protected persistent storage, independent of boot. Before each collector start/reexec, reserve last+1 under one source-local lock, durably fsync the counter and directory, then choose a fresh generation_id and observe boot_id. Numbers are never reused, including failed starts. Missing/corrupt counter means source publication disabled/UNAVAILABLE; do not reset to 0. A boot transition MUST increase this same host-wide counter, so UUID order and clocks are irrelevant. Saturation refuses publication. Commissioning seeds the counter explicitly; not an automatic recovery from missing storage.

Current transition proof: a reviewed operator/commissioning verifier on the SOURCE observes boot identity, actual collector PID/start/executable/argv, durable reserved counter, current committed snapshot tuple/hash and the reviewed source/profile. Select DIRECT reviewed reader-local console provisioning of that exact tuple and saved proof; the operator authenticates to Intel and installs the pin with Intel's local validation key, NEVER through the status response or another source-served signed cache. The proof observation and installation form one serialized commissioning window with source collector lifecycle writers suspended; recheck the source tuple at the end before enabling the reader. This freezes the trust path; operator/verifier ownership and the actual commissioning receipt remain due. Without independent provisioning/lifecycle coordination, the implementation remains UNAVAILABLE/TRANSITION_UNVERIFIED. Verifier confirms the current incarnation at that observation; proof is a saved receipt, not a timestamp guess. No automated source command/helper is added by this proposal.
