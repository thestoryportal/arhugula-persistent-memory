- **C as written:** preserves C:85, “does not change, replace or relax `tools/c10w_p2_gate.py`”; C:87, “Every dispatch-capable science helper is registered before release to run”; and C:115, “failed registration must leave no released I/O child,” by refusing before root release. No C amendment; positive launch coverage remains OPEN under C:119.

- **Launch/bytes:** add the refusal before the existing admission path; do not run the gate or payload on refusal. Science source, engine and gate bytes remain unchanged; positive C10W dispatch is unavailable under this option, consistent with its current worked-example status (DR:20).

### 1B. Keep C; instrument a closed, non-SIP launch runtime — large, conditional

Use a pinned native interposer on every permitted spawning runtime: hold posix_spawn children suspended and hold fork children inside a control-only rendezvous before returning to the caller. Independently enroll exact identities and capability scope, durably acknowledge them, then release; fail closed if any spawn path can escape that protocol. This is a candidate requiring a complete coverage proof, not an established feasible solution for the present runtime.

- **C as written:** intended to satisfy C:87, “Every dispatch-capable science helper is registered before release to run,” and C:115, “PID plus start identity, parent/group identity and capability scope” / “failed registration must leave no released I/O child”; preserve independent orphan accounting (C:117) and the unchanged gate (C:85). - **Mac feasibility:** documented: dyld(1) supports library injection and excludes SIP-protected binaries; posix_spawnattr_setflags(3) supports pre-user-space suspension. checked: the alternative bash and Python have the arm64/ad-hoc signatures above. Interception of CPython's actual fork/vfork/posix_spawn routes, shell subshells, exec transitions, stripped environments and native bypasses is **not established**; fork rendezvous correctness is also not established.
- **Launch/bytes:** the launcher would select a pinned non-SIP shell and inject the interposer; protected absolute descendants such as `/usr/bin/git` need a reviewed alternative runtime or proved nonspawning leaf treatment (reader: `experiments/track_c/c10w_oracle_read.py:133–135`). Science scripts, engine and gate bytes stay unchanged, but executable dependencies/environment and runtime behavior change; this is **not** proof of an unchanged science edit path or scientific equivalence. ## Fork 2 — guard invocation, sandbox identity and execution

The SCIENCE `/invocation` is ScienceInvocationProfile (J4:4784–4786), which forbids sandbox fields (J4:10547–10556); GUARD is an ordinary Process role requiring a sandbox hash (J4:375–381,400–418). Its supplied profile has `exec_paths=[]`, `deny_fork_exec=true`, yet it is assigned admission/payload execution (J4:14158–14174; F5:26; V7:15–21).

### 2A. Sandboxed control guard; broker performs science execution — medium

Keep `science-guard` as canonical `/invocation`, but type that invocation as ordinary InvocationProfile with the required GUARD SandboxProfile. After authenticated clearance consumption and durable RUNNING, it delegates exact admission/payload requests to a separately provisioned, enrolled **unsandboxed science launch broker**; admission must succeed before payload release. This keeps the guard restricted but explicitly trusts the separate broker, rather than pretending the present sandboxed coordinator can launch unrestricted science.

- **C as written:** preserve C:85, “does not change, replace or relax `tools/c10w_p2_gate.py`”; C:87, “commits `RUNNING`; it then runs its existing admission/dispatch checks”; C:115's exact pre-release identity/scope and failure rule for broker-launched roots. No C amendment for this composition; science descendants independently need the Fork-1 decision.
- **Freeze changes:** revise SCIENCE's `/invocation` type (J4:4784–4786; F5:103), replace guard execution with delegation (F5:26), and bind the whole construction to one context (V7:67,75). Add a distinct SCIENCE_LAUNCH_BROKER Process/invocation exemption to the all-ordinary-roles sandbox rule (F5:70); do not disguise it as SCIENCE_PAYLOAD or exempt transfer brokers. Retain DR:24's guard ownership. MAESTRO must select/Astra review the new trusted role, authenticated one-use delegation, bootstrap enrollment and profiles; no C relaxation is implicit.
- **Mac feasibility:** documented: sandbox_init(3) can sandbox the guard; sandbox(7) makes parent restrictions inherit; posix_spawnattr_setflags(3) provides suspended creation. Provision the science broker from a parent without the guard/coordinator's restrictions, before delegation; merely spawning it from the current coordinator is insufficient because that policy denies memit writes (F5:262). No removal of an inherited sandbox is assumed. Broker bootstrap, runtime identities and successful A16a composition are **not established** (C:119,163).
- **Launch/bytes:** reuse F5:260's suspended enrollment primitive in the separately profiled broker, never the restrictive coordinator's science-child spawn path. Guard uses authenticated IPC; broker enrolls/releases existing admission, waits for success, then enrolls/releases the exact science entrypoint under the same launch/nonce. Failed admission retains exclusion until explicit cancellation (C:87–89); a detached gate result cannot replace checks inside the existing wrapper. Science source/engine/gate bytes stay unchanged; native broker/guard, bootstrap, schemas and profiles change. Broker absence/failure refuses; uncontained broker capability and all descendants require C:89,117 accounting.

Give the native guard a dedicated unsandboxed control-role Process/Invocation type instead of borrowing the science-payload exemption. It owns clearance consumption and exact suspended admission/payload launches, with no direct authority or bulk-write capability assigned; it remains a distinct recorded control process. This removes the sandbox contradiction by explicitly enlarging the trusted launch component.

- **C as written:** preserve C:85's unchanged gate, C:87's RUNNING/check sequence, C:115's identity/capability registration and C:117's full independent accounting. No C clause explicitly requires a sandbox field in C:85–119, so no C amendment is needed for guard typing alone; this does **not** weaken descendant enrollment, which still needs the separate Fork-1 decision.
- **Freeze changes:** revise GUARD's ordinary sandbox requirement (F5:70; J4:375–381,400–418), replace its deny-fork/exec profile obligation (J4:14158–14174), and introduce a role-specific invocation type rather than misclassifying the guard as SCIENCE_PAYLOAD (F5:100; V7:17–21). Provisioning, actual admitted command forms and policy-free startup on this host are **not established** (C:119,163).
- **Launch/bytes:** native guard directly brokers unchanged admission and existing payload, preserving launch-scoped identity and explicit cancellation. Science source, engine and gate bytes stay unchanged; native guard/schema/profile bytes change, and the guard loses a containment boundary. Bytes alone do not prove admission compatibility (C:163–165).

**Recommendation — Fork 2:** select **2A**, retaining the ordinary guard's sandbox identity/deny-fork/exec restriction while assigning spawn power to one explicitly trusted science broker (F5:70,260; J4:14158–14174).
