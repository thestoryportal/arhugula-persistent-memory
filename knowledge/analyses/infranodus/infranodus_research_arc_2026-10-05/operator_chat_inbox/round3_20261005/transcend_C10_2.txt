Role-decomposed editing: what retrieval and video already know that C10 doesn't

The shared failure, stated precisely

Three literatures, one pathology: a single anchor cannot survive reformulation of its context.

C10: write anchored at one token (last prompt), one band, one value. Paraphrase 0/72. Hidden-state transfer 0.8–1.8% at any ridge — the anchor simply isn't reconstructed by the reformulated prompt.
Naïve RAG: one index (dense or sparse). Query reformulation moves the embedding off the anchor; recall collapses. The RAGPart/RAGMask finding is the dual — retrieval anchors on literal tokens, not task structure, which is exactly your keygram rank-1.02 collapse in a different currency.
Autoregressive video: context anchored on the tail alone. Error accumulates over rollout because short-term continuity is the only anchor there is.

The naming in your own graph is almost embarrassing: `edit ↔ single` carries the labels paraphrase, token, subject, multus, band. The single/multus axis is the live variable, and it's categorical.

---

What the two solved cases did

Hybrid RAG (Blended RAG, HyPA-RAG, HetaRAG). They did not tune a single retriever harder. They refused to pick one index: dense + sparse + KG, blended by a query-complexity classifier that routes adaptively. The gain comes from heterogeneous anchors with a routing rule — not from better anchors.

Relax Forcing. Three functionally distinct roles: Sink (global stability), Tail (short-term continuity), History (mid-range motion). The selection criterion is the sharp part — History frames are chosen to maximise alignment with global anchors while suppressing redundancy with recent context. That is a diversity objective over memory slots, training-free.

Both are the same move: role-decompose the anchor, add a selection rule that penalises redundancy.

The Asymmetry, Unpacked

The statement: routes 1 and 3 attack the same quantity — tokens-per-value — but route 3 edits per token while route 1 reduces the token count.

Why they're the same quantity

CORPUS/35's own diagnosis: coined values tokenize at 4–5.5 tokens, and full-sequence exact-match compounds per-token failure. If each token realizes with probability p, the A7 parafull you measure is roughly pⁿ. Your 19–31% at n≈5 implies per-token p ≈ 0.72–0.79 — not catastrophic per token, catastrophic only under exponentiation. That exponent is the whole C10 residual.

Two ways to attack pⁿ:

AnyEdit (route 3): raise p → 1 by writing each token position explicitly. Fixes the base.
Short codes (route 1): drop n from 5 to 4 — or, more aggressively, to 1 if the value is a single minted token. Fixes the exponent.

Same product, opposite factor. Nothing in CORPUS/36–38 distinguishes them, because the band knobs and 4–12 sweeps touched neither — they tuned where and how wide the write lands, not how long the value is.

The Transcending Move: Stop Editing Facts, Edit the Tokenizer's Prior

Every route on the table — AnyEdit, short codes, KILM, band knobs — accepts one unexamined premise: the value must be written as a sequence the model emits token-by-token under a next-token objective. C10 fires because that objective compounds. But the compounding isn't a property of the value. It's a property of the decoding regime.

The statement

> A multi-token value is only fragile because you ask for it autoregressively. Make the value's realization non-autoregressive and the exponent disappears — not reduced, structurally absent.

Fast SceneScript is sitting in your corpus as a tokenization paper and you've been reading it as one. It isn't. It's an existence proof that structured outputs can be emitted by multi-token prediction heads with self-speculative verification, converting an n-step serial gamble into a one-step parallel commit plus a cheap accept/reject. The accuracy loss MTP normally incurs — "unreliable token predictions" — is exactly the pⁿ problem, and SSD is their fix for it.

Your A7 values are structured outputs. Project-coined multi-word terms are closed-form, enumerable, known-at-write-time. You are using an open-vocabulary autoregressive decoder to emit strings you already have in full at edit time.

The concrete form

At write time you know the full target. So:

Make the edit install a selector, not a sequence. One key at the subject's last token (CORPUS/43 already licenses this — subject-keyed singles transfer 18/18), writing a value vector that a short multi-token-prediction head decodes in one parallel commit, with self-speculative verification as the accept test. The pⁿ exponent stops existing because there is no n-step serial chain to compound. Fast SceneScript's own framing: MTP alone degrades, SSD recovers it — the pair is the mechanism, not either half.

This is not AnyEdit (which writes n keys for n tokens — still serial, still 17 CUDA bindings, still a struck anchor). It's not short codes (which shrink n but keep the chain). It changes the shape of the read, which no arm in CORPUS/35–43 has varied. Every one of those runs used greedy autoregressive full-sequence exact-match as the measuring instrument — and that instrument is also the failure mode.

What this predicts, falsifiably

If the exponent is decoding-regime-induced rather than value-induced:

Teacher-forced per-token accuracy (already 60.2% at baseline, 34.0% at later band) should upper-bound parallel-commit accuracy, not equal it — the chain was costing you more than the tokens were.
The A7 ↔ A1/A2 gap should compress, because single-token values never paid the exponent and multi-token ones stop paying it.
The gap should not compress if the real deficit is prior-absence — in which case coined values are fragile wherever they're read from, and cluster 4 is the true blocker, not cluster 3.

The one-run test that separates all three hypotheses

Take the 24 A7 values. Score each under three reads at the same checkpoint:

| Read | Measures | If high |
|---|---|---|
| Teacher-forced full continuation | is the value in W | write succeeded |
| Free-running, first token constrained to gold | does the chain recover given a correct start | exposure bias is the gap |
| Free-running, unconstrained (= current parafull) | deployment number | — |

TF high, constrained high, unconstrained low → first-token failure dominates (exactly the ACL MoE anecdote: "the first word is incorrect, the remaining part correct"). Fix is first-token-targeted, cheap, no port.

TF low → the write never landed. Back to AnyEdit, and the port is justified.
