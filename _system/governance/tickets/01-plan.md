# Stage 1 — Plan (TD/PLAN.md)
Part of the tickets guide. Router: `_system/governance/TICKETS.md`. Roots (L, M, S, W, TD, MEM, HO): `00-roots-and-roles.md`.

The plan shape is in S/SKILL.md §1. What the skill does not say, and what has cost re-cuts:

- The first line is `Approved: <short pointer>`, written only after the operator approves, and never by you on your own reading of "sounds good". A draft carries no `Approved:` line at all: the cut's regex (S/scripts/tickets.py:19) accepts any text after it, so a placeholder like `Approved: pending` passes as an approval. Keep the line a short pointer and put the operator's quotes in an "Approval record" section of the plan, because the approval text is copied into every ticket and counts toward the 2048-byte cap; dry-run a cut in scratch to check the cap [R11].
- One step = `## Step N: <observable result>`, with `write:` (at most 4 files), `test:`, `out:`, optional `deps:`, `reads:`, `astra:`. The heading becomes the commit message and the PR title (tickets.py:250, :254), so write it as a result anyone can check, not as a task name [R12].
- A step that must run in M itself and stage more than 4 files is not a ticket. A unit move is an example: it stages 11 entry files plus one split per unit, and the run core refuses a linked worktree. Such a step is a MAESTRO integration step. It runs on a `tk/T<step>` branch in M and lands through `L/land.sh <PR> M`, never through tickets.py close or ship.sh (T215-AMENDMENT.md A5; `L/part2/followup-366/PLAN.md` ruling R10). Do not split its write list into tickets that can never pass `tickets.py check`. Mark any ticket JSON it supersedes in that JSON's `rules` field, so no later session cuts it.
- `out:` holds the step's requirements as numbered sentences, `(1) ... (2) ...`, as Steps 318-324 in `L/w1opt/followup-318/PLAN.md` do. Numbers let the reviewer, the prober and MAESTRO's ruling name a requirement by number. S/SKILL.md §1 says the same since Step 326 (installed 2026-10-17); its template line is `out: (1) <one checkable requirement> (2) <the next one>`.
- Number new steps after the last used id, across all TDs: ids become branch names, and the close finds a dependency by its `T0NN:` commit subject, so a reused number collides with history [R10].
- Width rule: at most 2 steps may write any one file, counted over every ticket in the TD, merged ones included (tickets.py:14, :184). When a third writer is needed, move a not-yet-built ticket's write into a new leaf file; do not raise the cap, because the cap is what lets lanes run in parallel without merge conflicts. Two steps that write one file also get an automatic dependency in plan order (tickets.py:76-79), so they never run in parallel: the second waits for the first to merge, which adds a wave and a full ticket's minutes to the estimate. Follow-ups that need a hub file whose two writers already merged go in a TD of their own, which the cap counts separately (STEP41 ruling, `L/recut/followup/`; plan 318 likewise lives in `L/w1opt/followup-318`) [R14].
- `test:` strings: anchor unittest output as `grep -qE "Ran [1-9][0-9]* tests? in [0-9.]+s +OK *$"`. Unanchored, `discover` of a missing file prints "Ran 0 tests ... OK" and a skipped method prints "OK (skipped=1)", and both pass as GREEN [R17].
- `astra: yes` only for gate, validator or destructive code, and such a step writes its own new test file (the cut refuses otherwise).
- Frozen-suite check: a step that changes a tool's default, or the path its calls take, can break tests in existing suites that no write list names. Before the cut, search every existing suite that calls that tool (for guard_mutants: `M/code/ops/review/test_guard_mutants*.py`) for two shapes: a patch of a function on the changed path (`mock.patch.object(<module>.<Class>, "<fn>", ...)`), and an assertion that a new `out:` sentence contradicts (for example `assertNoScratchLeft` against "a refusal keeps the scratch"). Rule on each hit before dispatch, as `L/w1opt/followup-318/reviews/wave-b/RULING.md` (F1-F3) did: widen the write list and bound the edits, or change the step. Also run on master every acceptance command that a brief will name; a command that already fails there cannot be the builder's bar. You will write "the existing suites run under the new default and must pass unchanged" and think it is a safe requirement. It is a claim about tests you have not read. T330 lost a full fix round to it: 6 of 95 frozen tests assumed one run at a time, and one grep shows both shapes (`L/w1opt/followup-327/reviews/T330/RULING.md`). In the same plan, the T328 brief required `--head-oracle` to exit 0, and it already failed on master (HO/HANDOFF-STEP66.md, Traps) [R54].
- Size: a step is atomic when one builder can take it from dispatch to merged in 15 minutes. Split a step that you expect to change more than about 100 product lines, or that adds more than one new mechanism (a refactor plus a feature built on it is two). The behavior-preserving part becomes its own step first, with every existing suite passing unchanged as its bar; the new behavior is a second step that depends on it. The cut's "oversized ticket" refusal does not see this: it counts the ticket file's bytes (MAX_BYTES 2048, tickets.py:15), not the change. You will look at a step with one clear goal and think *"one goal, one ticket."* One goal can still carry two mechanisms. T330 (122 product lines and a 503-line test file: a run-as-generator refactor plus the `--jobs` scheduler) passed the cut and took more than 60 minutes before its first ship. Each revert-gate run of its own 10.6 s test took about 5 minutes [R55].
- MAESTRO steps (changes to L/tools or the skill) go in the same plan under `## MAESTRO step N:`. That heading does not match the cut's `## Step N:` pattern (tickets.py:20), so the cut never turns them into tickets; they follow Stage 11 (`11-maestro-steps.md`). But a field line (`write:` `test:` `out:` `deps:` `astra:` `reads:`, also as a `- ` or `* ` bullet, tickets.py:21) under a MAESTRO heading still attaches to the `## Step` before it (tickets.py:46-54): it fails the cut as "given twice" or silently adds the field to that ticket. Write MAESTRO step sections with no line that starts with a field name; use numbered items, as Steps 325-327 do.
