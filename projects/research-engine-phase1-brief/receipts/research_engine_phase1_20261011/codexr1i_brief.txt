== Design decisions already made (MAESTRO) ==
R1, one terminal authority: the `.exit` file is written exactly once with the final status and is never rewritten. A new receipt `<prefix>.final` is the only success authority. Create it with O_CREAT|O_EXCL only after stdout, stderr and `.exit` are each fsynced and the directory is fsynced, and only if an M3 reading taken after those syncs is ≤ the deadline. Its bytes are one canonical JSON line: {"exit": 0, "qualified": true, "m3_deadline": ..., "m3_qualified_at": ...}. Then fsync it and the directory. Bind consumption, inventory's `require_anchor()` and successor acceptance all require the committed `.final` with exactly those fields and exit 0 matching `.exit`. A missing, partial or unparsable `.final` is a dead end that needs operator-reviewed recovery, never a retry. Charge the `.final` bytes to the capture's receipts. An expired deadline still blocks any later dispatch.
R2, round-trip start: the stub's earliest action is reading time.monotonic() as T0. It then verifies the bundle (one newline-terminated line on stdin), writes `R1I-READY <sha256 of the request member>` as its first stdout line, and waits for one stdin line `R1I-GO <budget_seconds>`. Before GO it does no fetch and no write. The wait is capped by a v8 constant `/budget/pre_go_cap_seconds` measured from T0. Stdin EOF, malformed GO or the cap expiring → exit nonzero, nothing written. The M3 dispatcher uses subprocess.Popen (no new dependency). It reads the READY line and computes budget = deadline − now() − margin at the moment it sends GO. It refuses (and kills ssh) if budget ≤ 0. Intel stops before any fetch or write once monotonic() − T0 ≥ budget. Why: T0 precedes the M3 reading the READY line, so Intel's end ≤ GO-send time + budget = deadline − margin, whatever the preparation or transport delay. The report states this bound and that clock-rate drift (≤ 100 ppm over 870 s < 0.1 s) sits inside the margin. The M3 writes every stdout byte, READY line included, to the capture file unchanged. The M3 hard timeout at the deadline stays. On stdout or stdin failure after GO (disconnection), the collector stops before its next fetch or write and exits nonzero.
R3, receipts: extend the existing J:1466 accounting ("All inventories, stdout/stderr and evidence", 10,000,000 bytes); do not create a parallel ledger. M3 receipts (attempt records, every bind/inventory .json/.stderr/.exit/.final, successful and failed alike) are charged. The charge is measured from the on-disk sizes of the files matching v8-listed patterns, not from a separate counter. Before dispatch, the M3 refuses unless remaining allowance ≥ a v8 per-dispatch bound `/budget/max_dispatch_receipt_bytes`. During dispatch, it stops reading and kills ssh when stdout+stderr would pass that bound, and records the run as failed. Failed-run receipts are retained and stay charged.
R4: M reads the transit margin from the sealed v8 `/budget/transit_margin_seconds`; no literal 5 remains in M. The report says evidence updates are usable only inside the original 870 s window from the bind start; anything later needs separately reviewed recovery. Correct D:4's V:79–81 and D:18's T:1551 citations and M:1's "Every mode writes stdout only" comment.
